# i18n — język UI i treści

## Podział

| Rodzaj tekstu | Gdzie | Mechanizm |
|---------------|-------|-----------|
| Komunikaty walidacji / API (stałe) | Backend | `gettext_lazy` (`_()`) |
| Etykiety UI, buttony, empty states | Frontend | i18n framework projektu (i18next / expo-localization + JSON) |
| Treść katalogu / CMS (produkty) | DB | `JSONField translations` + helper odczytu |

Język **prozy agentów** (docstringi, commity) ≠ i18n produktu — to MCP
`get_language` / `--language`.

## Backend

- Stringi dla użytkownika końcowego w serializerach → `_()`.
- Format błędów: `arch:api-errors`; tłumaczenie po `Accept-Language` /
  `request.LANGUAGE_CODE` gdy włączone.
- Treść dynamiczna: pola w `translations` definiuje serializer wpisu; odczyt z
  fallbackiem (np. `pl` → domyślny) w helperze (`common/helpers/i18n` lub równoważne).

## Frontend

- Klucze tłumaczeń, nie hardcode PL w komponentach feature (wyjątek: prototypy).
- Format dat/liczb: `Intl` / lib projektu wg locale użytkownika.
- PaymentSheet / natywne SDK: locale osobno (`capability:payments:expo-stripe`).

## Zasady

1. Kod, identyfikatory, slugi URL, nazwy pól JSON API → **angielski**.
2. Nie mieszaj ręcznego camelCase tłumaczeń z automatycznym parserem API.
3. Brak klucza i18n → widoczny fallback (klucz lub język bazowy), nie cichy pusty string.

## Powiązane

- `core:language-pl` / `core:language-en` — konwencje kodu i prozy
- `arch:api-errors`
- `stack:django-drf:backend-standard` — JSONField translations
- `arch:ui-ux-expo` — copy / a11y
