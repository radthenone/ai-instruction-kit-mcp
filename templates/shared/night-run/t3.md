# Karta transportu T3 Code dla @KIT_CMD_PREFIX@night-run

Karta transportu dla procedury `@KIT_CMD_PREFIX@night-run` w środowisku T3 Code (plik instalowany jako `.ai/night-run-t3.md`).
Zastępuje transport procedury `@KIT_CMD_PREFIX@night-run` (uruchamianie i nadzór zadań, sprzątanie, raportowanie), nie zmienia kroków procedury zlecenia ticketu (`night-run-ticket`).

## 1. Sesja ticketu (orkiestrator → dziecko ticketu)

Orkiestrator nocy uruchamia sesję dla każdego ticketu za pomocą narzędzia `delegate_task`:
- `isolation: worktree` — T3 tworzy izolowane worktree dla sesji ticketu z plikami kita i środowiskiem `.venv` (przygotowanymi przez hak `post-checkout`), a T3 nadaje temu worktree własny branch;
- `mode: async` — uruchomienie asynchroniczne;
- `clientRequestId` — klucz idempotencji złożony z nazwy katalogu CTX i numeru ticketu (np. `<nazwa katalogu CTX>-<numer ticketu>`); ponowienie z tym samym `clientRequestId` nie tworzy drugiego dziecka;
- `task` — wskazuje procedurę `night-run-ticket`, podaje parametry zlecenia (baza `<BASE>`, ścieżka `<CTX>`, nazwa brancha `<typ>/<N>-<slug>` (ta sama wartość co `title`; sesja ticketu jej nie wyprowadza), handoffy blokujących, treść issue, reguły) i wprost zezwala na dalszą delegację (sesja ticketu ma pełne prawo delegować implementację i podzadania);
- `role: general`, `title: "<typ>/<N>-<slug>"` — tytuł to nazwa brancha z konwencji kita (`@KIT_CMD_PREFIX@git-start`, np. `feat/475-enforce-branch-naming`), z której T3 wyprowadza nazwę brancha worktree; nie wolny tekst.

Sesja ticketu zaraz po starcie (przed `@KIT_CMD_PREFIX@git-start #<N>`) najpierw sprawdza bazę: `git fetch origin` (błąd fetch → needs-human); niepusty `git status --porcelain` (brudne worktree) → needs-human; gdy `git merge-base --is-ancestor HEAD origin/<BASE>` zwraca 0 i `git status --porcelain` jest pusty, wykonuje `git merge --ff-only origin/<BASE>` (inny PR zmergował się po utworzeniu worktree); potem `git merge-base --is-ancestor origin/<BASE> HEAD`. Niezerowy kod wyjścia (rozbieżna historia albo brudne worktree; baza się nie zgadza → needs-human): bez zmiany nazwy, bez ponownego użycia brancha, ticket nie jest kontynuowany. Potem sprawdza `git branch --show-current`. Gdy T3 nadało inną nazwę niż `<typ>/<N>-<slug>` z `task`, natychmiast wykonuje `git branch -m <typ>/<N>-<slug>` (przed pierwszym commitem i push), żeby PR powstał pod nazwą z konwencji. Pusty wynik (odłączony HEAD) → `git switch -c <typ>/<N>-<slug>`. Branch o tej nazwie już istnieje (odmowa `-m`) → needs-human, nigdy `-M`. Potem `@KIT_CMD_PREFIX@git-start` użyje aktywnego brancha `<typ>/<N>-<slug>` zamiast tworzyć nowy.

PR sesji ticketu (`gh pr create`, krok 6 `night-run-ticket`) dostaje wszystkie etykiety issue flagami `--label`; etykiety procesowe stanu (`ready-for-agent`, `ready-for-human`, `needs-info`, `needs-triage`, `wontfix`) są odrzucane. Tytuł PR to czysty Conventional Commit po angielsku opisujący zmianę domenową, bez prefiksu `(night-run)`.

Sesja ticketu tworzy PR w kroku 6 i zwraca jego URL dopiero w hand-backu, więc orkiestrator woła `write_pull_request_guides(pullRequests: [{url: "<URL PR>"}])` po otrzymaniu hand-backu z URL PR, nie w trakcie review, żeby w zakładce PR Guide w T3 Code powstał przewodnik po zmianach PR.

Limit providera (429 / quota) w sesji ticketu albo wykonawcy → bez cichej zmiany providera. Rotacja jest dozwolona tylko wtedy, gdy parametry nocy podają zapasowego wykonawcę (`zapas: <wykonawca> <model>`): kolejne zadania dostają `target.providerInstanceId` i `target.model` z tego parametru; działa w obie strony (`antigravity` ↔ `claudeAgent`), ale tylko na podstawie parametru. Sesja ticketu, która dostała limit, startuje raz od nowa przez `delegate_task` na zapasie z `clientRequestId` o sufiksie `-zapas`; nowy `taskId` sesji zastępuje stary w `## Stan`. Po ponowieniu na zapasie orkiestrator zapisuje w `## Stan` użytego wykonawcę i model (`zapas: <wykonawca> <model>`). Ponowienie po limicie wykonawcy wykonuje sesja ticketu na zapasie; wpis `## Stan` pozostaje bez zmian (`taskId` sesji ticketu). Pola `night-run.clean-slate` z Profilu mają pierwszeństwo przed zapasem (sekcja 7). `zapas` z tym samym providerem co bieżący albo bez modelu → needs-human. Bez parametru `zapas` limit → needs-human. Limit także na zapasowym (wyczerpanie obu providerów) → needs-human, bez pauzy, `sleep`, `ScheduleWakeup` ani odpytywania o reset limitu; wznowienie robi człowiek.

## 2. Wykonawca implementacji (z sesji ticketu)

Gdy ticket wymaga delegowania wykonawcy implementacji (kroki 2–3 w `night-run-ticket`):
- delegowanie wykonuje sesja ticketu (z sesji ticketu), a nie główny orkiestrator nocy;
- wywołanie `delegate_task`:
  * `isolation: shared` — wykonawca pracuje w checkoucie sesji ticketu, na branchu roboczym sesji ticketu z `@KIT_CMD_PREFIX@git-start`;
  * `mode: async`;
  * `task` — specyfikacja zadania implementacyjnego, testy z timeoutem, log postępu w CTX oraz obowiązkowy hand-back.

### Mapowanie modeli na `target`

Parametry nocy `implementacja: <wykonawca> <model>; review: <wykonawca> <model>` sesja ticketu tłumaczy na obiekt `target` w `delegate_task` (osobno dla implementacji i dla review):

| `<wykonawca>` | `providerInstanceId` | `model` (przykład) | `options` (przykład) |
|---------------|----------------------|--------------------|----------------------|
| `claude` | `claudeAgent` | `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5` | `[{id: "effort", value: "medium"}]` |
| `codex` | `codex` | model z listy providera | `[{id: "reasoningEffort", value: "medium"}]` |
| `antigravity` | `antigravity` | model z listy providera | `[{id: "thought_level", value: "high"}]` |
| `opencode` | `opencode` | `<provider>/<model>` z listy providera, np. `opencode/deepseek-v4.1-flash-free` | `[{id: "variant", value: "high"}]` |

Przykład: `review: claude claude-haiku-5-5` → `target: {providerInstanceId: "claudeAgent", model: "claude-haiku-5-5"}`, a review idzie z `role: review`, `mode: wait`, `isolation: shared`.
- konfiguracja w `.ai/project.profile.yaml`: jeśli profil projektu zawiera blok `targets.<wykonawca>.<tier>` (gdzie tier to `light`, `standard`, `heavy`), a parametr zlecenia nie podaje konkretnego modelu lub opcji, orkiestrator bierze pola wpisu: `providerInstanceId` zawsze, `model` i `options` tak, jak wpis je podaje (domyślnie `standard` dla implementacji, `heavy` dla review); przejęcie ticketu w T3 bierze `targets.<wykonawca>.takeover` (brak wpisu = kopia `standard` tego wykonawcy); pole podane jawnie w parametrze nocy nadpisuje wpis, a jawny parametr nocy ma zawsze pierwszeństwo przed konfiguracją w profilu;
- przed pierwszym `delegate_task` w sesji: `orchestrator_capabilities`; nazwy modeli i `options` bierz z jego wyniku, nie z pamięci; `providerInstanceId` w tabeli to nazwa domyślna — gdy w wyniku `orchestrator_capabilities` jest wyłączona albo jej nie ma → needs-human; nie wybieraj innej instancji tego samego `driverKind`, nawet gdy włączona jest dokładnie jedna (np. `opencode2`);
- options: z wpisu profilu albo z parametru nocy (np. `@poziom`, `#wariant` w nazwie modelu lub parametr `effort:` / `variant:`) albo provider ich wymaga; poziom wysiłku orkiestrator tłumaczy na właściwą opcję providera: `id: "effort"` (Claude), `id: "variant"` (OpenCode), `id: "thinking_level"` (Antigravity); brak wskazanego poziomu i brak `options` we wpisie → pomiń `options` (provider używa wartości `default` z `orchestrator_capabilities`); brak `<model>` w parametrze i we wpisie → pomiń pole `model` (domyślny model providera);
- provider albo model niedostępny → needs-human, bez cichej zamiany na inny model i bez fallbacku na natywne narzędzia.

## 3. Stan i wznawianie

- Identyfikator zadania `taskId` i identyfikator wątku `childThreadId` zwrócone przez `delegate_task` zostają zapisane w `## Stan` w pliku CTX (`ticket: #<N> taskId: <taskId> childThreadId: <childThreadId>`);
- po przerwaniu sesji orkiestratora lub restarcie wznowienie następuje przez odpytanie `task_status` na podstawie zapisanego `taskId`; `childThreadId` wznowienie odczytuje z tego samego zapisu i przekazuje do kroku 5 sekcji 5 (`t3_thread_organize` z `threadId`);
- ponowienie wywołania z tym samym `clientRequestId` nie tworzy drugiego dziecka.

- Karta eskalacji needs-human (sekcja „Karta eskalacji” w `night-run`): pole `Wątek T3:` to wartość pola `link` z wyniku `delegate_task` sesji ticketu, wstawiona dosłownie.

## 4. Watchdog i cron

- watchdog i cron pominięte: w środowisku T3 nie uruchamia się skryptu `.ai/night-run-watchdog.sh` ani `CronCreate` (T3 samodzielnie zarządza cyklem życia zadań i wątków w tle).
- oczekujące prośby: orkiestrator sprawdza `t3_pending_request(action: 'list')` po każdym `delegate_task` i przy każdym `task_status` i automatycznie zatwierdza (`action: 'respond'`) wyłącznie pytanie o zaufanie do worktree utworzonego przez tę noc (ścieżka pod katalogiem worktree T3 tego uruchomienia, porównana ze ścieżką worktree sesji ticketu z wyniku `delegate_task`; brak pewności dopasowania → needs-human). Każdy inny oczekujący dialog (także uprawnienia narzędzi) nie jest zatwierdzany automatycznie: ticket → needs-human z opisem dialogu w raporcie.
- nasłuch PR reaktywny, zamiast pętli `gh pr checks --watch` (ani `sleep`, `Monitor`, `ScheduleWakeup`): zaraz po `gh pr create` orkiestrator woła `link_pull_request` z pełnym URL PR, potem `watch_pull_request`; T3 wybudza orkiestratora po zakończeniu checków albo przy nowym komentarzu lub review, a orkiestrator kończy turę zamiast czekać;
- `unwatch_pull_request` po `MERGED`, po decyzji needs-human dla PR i przed końcem nocy (NIGHT-RUN REPORT) — na każdym PR, który orkiestrator obserwuje.

## 5. Uwagi CodeRabbit i sprzątanie po MERGED

Po wybudzeniu z `watch_pull_request` z nowymi uwagami CodeRabbit (autor `coderabbitai`) orkiestrator przekazuje je sesji ticketu (albo wykonawcy); po pushu poprawki zamyka tylko wątki zaadresowane tą poprawką, przez GraphQL:

```bash
gh api graphql --paginate -F pr=<N> -f owner=<owner> -f repo=<repo> -f query='
query($owner:String!,$repo:String!,$pr:Int!,$endCursor:String){repository(owner:$owner,name:$repo){pullRequest(number:$pr){
  reviewThreads(first:100,after:$endCursor){pageInfo{hasNextPage endCursor}
    nodes{id isResolved comments(first:1){nodes{author{login} path body}}}}}}}'
gh api graphql -f id=<threadId> -f query='
mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}'
```

- `reviewThreads` filtruj po `isResolved: false` i autorze `coderabbitai`; `id` wątku idzie do `resolveReviewThread(input:{threadId:$id})`;
- uwaga niezaadresowana albo odrzucona → wątek zostaje otwarty, z odpowiedzią w wątku (powód), nie zamykany po cichu;
- przed pushem poprawki odczytaj pełną treść wszystkich wcześniejszych review CodeRabbit ze wszystkich stron endpointu reviews (potok ze wszystkich stron jw., bez filtra `commit_id`: `set -o pipefail; gh api --paginate --slurp repos/<owner>/<repo>/pulls/<N>/reviews | jq 'flatten | map(select(.user.login == "coderabbitai[bot]"))'`) i uwagi wymagające działania przekaż sesji ticketu razem z uwagami z wątków;
- przed pushem poprawki w rundzie naprawczej sesja ticketu (albo wykonawca) przegląda całą zmienianą sekcję pod kątem listy znanych klas problemów (aby uwagi sąsiednich fragmentów nie wracały w kolejnych rundach): idempotencja i wznowienie po przerwaniu; kolejność zapisu stanu; polecenia o zakresie globalnym (np. `git worktree prune`); nadpisywanie plików ignorowanych; brak katalogu, rekordu lub pusty wynik; spójność z `git-end`;
- `reviewThreads` nie obejmuje uwag spoza diffu (sekcja „Outside diff range” w treści review) ani uwag ogólnych, a zdarzenie `watch_pull_request` niesie tylko skrócony podgląd komentarza; pełną treść review czytaj ze wszystkich stron (endpoint zwraca domyślnie 30 review na stronę, chronologicznie) przez `set -o pipefail; gh api --paginate --slurp repos/<owner>/<repo>/pulls/<N>/reviews | jq 'flatten | map(select(.user.login == "coderabbitai[bot]" and .commit_id == "<head>")) | last'` (pola `state` i `body`; w REST `user.login` autora `coderabbitai` to `coderabbitai[bot]`, `<head>` to bieżący head commit PR) — wybór ostatniego wpisu po wszystkich stronach, nie po pierwszej; uwagi wymagające działania z tej treści przekazuj sesji ticketu razem z uwagami z wątków;
- niezerowy kod wyjścia potoku (błąd `gh api`) albo pusty wynik → `needs-human` (błąd odczytu review), nigdy „brak uwag”;
- wynik `null` → review bieżącego head nie jest jeszcze odczytane: poczekaj na review bieżącego head (wybudzenie przez `watch_pull_request`) i nie przechodź do merge, dopóki go nie odczytasz; limit czasu (maks. 10–15 min) i postępowanie po jego upływie określa `git-end` (w rundzie 1 sprawdź otwarte wątki bota, a gdy ich brak — odnotuj brak review bota w raporcie; w kolejnych rundach `needs-human`); uwagi wymagające działania z wcześniejszych review nadal przekazuj sesji ticketu.

Gdy PR ticketu osiągnie stan `MERGED`:
1. Orkiestrator woła `unwatch_pull_request` dla PR (podpiętego wcześniej przez `link_pull_request`, sekcja 4);
2. Orkiestrator usuwa worktree sesji ticketu: `node .ai/worktree.mjs remove <katalog>`; gdy komenda zgłosi „Ścieżka nie istnieje”, orkiestrator sprawdza rejestrację worktree: `git worktree list` w głównym checkoucie repozytorium; gdy wpisu ticketu nie ma w `git worktree list`, przechodzi do kroku 3; gdy jedynym wpisem oznaczonym `prunable` jest wpis ticketu, uruchamia `git worktree prune` i dopiero potem przechodzi do kroku 3; gdy `prunable` jest także inny wpis, wpis ticketu wskazuje istniejący katalog albo `git worktree prune` się nie uda, sprzątanie zatrzymuje się i trafia do raportu, bez przejścia do kroku 3; inna odmowa zatrzymuje sprzątanie i trafia do raportu;
3. Orkiestrator usuwa lokalny branch ticketu: `git branch -d <typ>/<N>-<slug>` (branch nadany przez T3 po rename z sekcji 1);
4. odmowa -d (`git branch -d` zgłasza błąd / odmowę) -> wpis w raporcie, bez -D (zakaz `-D`, nigdy nie wymuszamy usunięcia przez `-D`).
5. Po krokach 2–4 (także po odmowie `-d` z kroku 4) orkiestrator archiwizuje wątek sesji ticketu: `t3_thread_organize(action: 'archive', threadId: childThreadId)` (`childThreadId` z wyniku `delegate_task` sesji ticketu); historia wątku zostaje w archiwum.

## 6. Pola raportu (NIGHT-RUN REPORT)

W końcowym raporcie nocy (NIGHT-RUN REPORT):
- Czas trwania: czas z wątków (na podstawie metadanych i znaczników czasu z zadań T3);
- Tokeny delegatów: tokeny delegatów „n/d”;
- Model: model „niepotwierdzony”, gdy `executedModel` jest `null` (np. dla wykonawców, w których T3 zwraca `executedModel: null`).

## 7. Clean Slate

Hand-back `clean-slate` (sekcja „Clean Slate” w `night-run`) → gdy spełniony jest warunek bezpieczeństwa z `night-run`, orkiestrator wykonuje kroki w tej kolejności; każdy zapis w `## Stan` to osobny krok:
1. zapisuje w `## Stan` etap `clean-slate: w toku` ze starym `taskId`, notatką o błędzie X i ścieżce Y oraz ścieżką worktree (`ticket: #<N> clean-slate: w toku, <stary taskId>, <ścieżka worktree>, notatka: <X, Y>`);
2. usuwa worktree ticketu (`node .ai/worktree.mjs remove <katalog>`);
3. zapisuje w `## Stan` etap `clean-slate: worktree usunięty`;
4. woła świeży `delegate_task` jak w sekcji 1, z różnicami:
   - nowy `clientRequestId`: `<nazwa katalogu CTX>-<numer ticketu>-clean-slate`;
   - `title`: `<typ>/<N>-<slug>-clean-slate`;
   - z `night-run.clean-slate` w Profilu: `provider` → `target.providerInstanceId`, `model` → `target.model`, `effort` → `target.options` jako `{id: "effort", value: <effort>}`; brak pola = wartość jak w sekcji 1; po rotacji brak pola = wartość z wpisu `zapas: <wykonawca> <model>` w `## Stan` (pola podane w Profilu mają pierwszeństwo);
   - Profil nadpisuje `provider`, a nie podaje `model` → nowe zadanie nie dziedziczy modelu z innego providera: bierze model z konfiguracji wybranego providera (`orchestrator_capabilities`) albo pomija `target.model` (sekcja 2); Profil nie nadpisuje providera: po rotacji provider zapasu zostaje (a model zapasu zostaje tylko wtedy, gdy profil nie podaje `model`); bez rotacji provider i model pozostają jak w sekcji 1;
   - `task` zawiera linię „Clean Slate: użyty” i notatkę zapisaną w kroku 1;
5. zapisuje nowy `taskId` i nowy `childThreadId` w `## Stan` w miejsce starych (`ticket: #<N> taskId: <taskId> childThreadId: <childThreadId>`).

Wznowienie bierze etap, ścieżkę worktree i notatkę z `## Stan`, nie z pamięci sesji:
- etap `clean-slate: w toku` i worktree istnieje → dokończ usunięcie i przejdź do kroku 3;
- etap `clean-slate: w toku` i worktree już nie istnieje → przejdź do kroku 4;
- etap `clean-slate: worktree usunięty` bez nowego `taskId` → przejdź do kroku 4.

Krok 4 przy wznowieniu podaje ten sam `clientRequestId`, więc T3 wznawia zlecenie bez nowego `taskId`; nigdy drugi `delegate_task` z innym `clientRequestId` dla tego samego Clean Slate i nigdy drugi Clean Slate na ticket.
